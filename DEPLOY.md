# Развёртывание

## Что сервису нужно от хостинга

| Требование | Почему |
|---|---|
| Постоянный диск | SQLite (`maptool.db`) — единственное хранилище |
| ≥ 1 ГБ RAM | пик Chromium с OCR-моделью — 416 МБ, плюс система |
| Процесс 24/7 | фоновое обновление в 3:00 и long polling бота |
| Исходящий HTTPS | qportal.kz, Nominatim, elicense.kz, api.telegram.org |
| Входящий HTTP(S) | сайт; для Telegram — **не нужен** (используется long polling) |

Отдельно: белый IP не требуется, домен не обязателен.

---

## Почему не Cloud Run

Три независимых препятствия, каждое из которых ломает что-то существенное.

### 1. SQLite на Cloud Run не заработает в принципе

Файловая система контейнера — в памяти, и при остановке инстанса
данные пропадают. Официальные тома тоже не спасают:

- **Cloud Storage через FUSE** — прямо из документации Google:
  *«Cloud Storage FUSE не обеспечивает контроль конкурентных записей
  в один файл (блокировки файлов)»*. SQLite требует POSIX-блокировок
  `fcntl()` и частичных записей по месту. Флага `--enable-sqlite`
  не существует — его нет и в исходниках gcsfuse.
- **Filestore** — Google действительно разрешает монтировать его в
  Cloud Run, но с оговоркой: *«Cloud Run не поддерживает NFS-блокировки.
  NFS-тома монтируются в режиме no-lock»*. Плюс минимальный тариф
  Filestore — 1 TiB, то есть $163,84 в месяц ради базы в 170 КБ.

Значит, базу нужно выносить наружу: Cloud SQL (Postgres, ~$15–25/мес)
или Firestore. Это уже переписывание слоя хранения.

### 2. Бесплатный тариф не оплачивает работу 24/7

| | Бесплатно | Нужно |
|---|---|---|
| vCPU-секунды | 180 000 | 2 592 000 (30 дней) |
| Покрытие | **6,9 %** | |

Стоимость всего бесплатного кредита — **$5,22 в месяц**. Конфигурация
`min-instances=1` с постоянно выделенным CPU (instance-based billing)
стоит **$51,80/мес** за 1 vCPU и 2 ГиБ. Request-based billing дешевле
($14,78/мес), но между запросами CPU урезается почти до нуля — и
планировщик в 3:00, и long polling бота там не работают.

### 3. Free Trial закрывается на 90-й день

Аккаунт Free Trial — $300 кредита на 90 дней. Если не перейти на
платный аккаунт с картой: аккаунт закрывается → ресурсы останавливаются
→ 30 дней пощады → **ресурсы удаляются безвозвратно**.

То есть «бесплатный» Google Cloud — это 90 дней, после которых либо
~$25/мес за машину, либо потеря данных.

### Итог по конфигурациям

| Конфигурация | SQLite | Задание в 3:00 | Бот | Стоимость |
|---|---|---|---|---|
| Free Trial, min=0 | ✗ стирается | ✗ CPU урезан | ✗ | $0 → всё пропадает на 90-й день |
| Платный, min=0 | ✗ стирается | ✗ CPU урезан | ✗ | ~$0 + 504 на долгих запросах |
| Платный, min=1, request-based | ✗ стирается | ✗ | ✗ | $14,78 — деньги за сломанное приложение |
| Платный, min=1, instance-based | ✗ **всё равно стирается** | ✓ | ✓ | $51,80 + внешняя БД |
| **Compute Engine** | ✓ | ✓ | ✓ | $0–$25/мес |

Cloud Run — неправильная форма для этого сервиса. Ниже — варианты,
которые работают.

## Вариант A. Oracle Cloud Always Free (бесплатно, ресурсов с запасом)

12 ГБ RAM, 200 ГБ диска, ARM. Лучший бесплатный вариант по объёму
памяти: пик Chromium в 416 МБ — это 3,5 % от 12 ГБ.

```bash
ssh -i ~/.ssh/<ключ> ubuntu@<ip>
curl -sSL https://raw.githubusercontent.com/cucumberbatch/ZhKhan-Agregator/main/deploy/setup_vm.sh | bash
```

Особенности:

- **Регион выбирается навсегда** — ставьте Франкфурт или Цюрих.
- **ARM.** `playwright` и `ddddocr` под aarch64 есть, но `onnxruntime`
  после 1.23.2 потерял cp310. В `Dockerfile` тогда нужен пин
  `onnxruntime==1.23.2` либо переход на Python 3.11.
- **Oracle может остановить простаивающий инстанс** (CPU, сеть и
  память ниже 20 % неделю подряд). Данные при этом сохраняются —
  останавливается машина, а не том.
- **Дефицит ресурсов A1** — создание приходится повторять при
  «out of host capacity».

## Вариант B. Google Compute Engine

Единственный бесплатный постоянно работающий ресурс в Google.
Бесплатные регионы — только США: `us-west1`, `us-central1`,
`us-east1`.

### Сколько стоит и что выбрать

| Машина | RAM | Цена | Вердикт |
|---|---|---|---|
| e2-micro | 1 ГБ | **$0** | Впритык, но рабочий вариант — подробности ниже |
| e2-small | 2 ГБ | $12,46/мес | Спокойный минимум |
| e2-medium | 4 ГБ | $24,93/мес | Комфортно, если есть ещё и другие задачи |

### e2-micro: что входит в 1 ГиБ

Бюджет памяти в момент обхода elicense.kz:

| Кто | МБ |
|---|---|
| Ubuntu + Docker | ~150 |
| Python-сервер | ~27 |
| OCR-модель (ddddocr) | ~100 |
| Chromium в пике | ~416 |
| **Итого** | **~690 из 1024** |

Запас есть, но без трёх страховок не обойтись:

1. **Swap.** Скрипт развёртывания создаёт 2 ГБ. Без него пиковый
   момент с Chromium упирается в OOM, и контейнер умирает вместе
   с браузером.
2. **Шапка контейнера.** `--memory=900m` — предел чуть ниже
   физической памяти, чтобы Docker выбивал процесс раньше, чем
   убьётся ядро.
3. **OCR-модель.** Она занимает ~100 МБ постоянно: Python-объект
   после выгрузки уничтожается, но onnxruntime держит свою арену и
   RSS не уменьшается (замер: 116 МБ до и после). Гарантированно
   вернуть эти мегабайты можно только вынеся OCR в отдельный
   процесс, — но при бюджете выше они и так помещаются.

**Главная проблема e2-micro — не память, а процессор.** Это
shared-core: документация прямо говорит, что E2 даёт «2 vCPUs for
short periods of bursting», то есть ядро делится между машинами.
Холодный старт Chromium (130 с на полной скорости) растянется
в несколько минут, а распознавание капчи — CPU-bound, и на
тротттлинге втрое-вчетверо медленнее.

Практическое следствие: **ночной обход перестаёт укладываться в
привычные полтора-два часа** и растянется на 3–5 часов. Это
не страшно, если он стартует в 3:00 ночи по Астане: закончит к
8:00 утра, когда сайт ещё не нужен. Но два обхода не должны
накладываться — планировщик ждёт следующих 3:00, так что
перекрытия не будет, пока обход укладывается в сутки.

Честная проверка — не расчёт, а замер на самой машине:

```bash
gcloud compute ssh zhkhan-vm --zone=us-central1-a
htop                        # во время обхода
docker stats zhkhan         # реальное потребление контейнера
```

### 1. Проект и биллинг

```bash
gcloud projects create zhkhan --name="ZhKhan"
gcloud billing projects link zhkhan --billing-account=ВАШ_БИЛЛИНГ_ID
gcloud config set project zhkhan
gcloud services enable compute.googleapis.com
```

Нужен **платёжный аккаунт с картой**: без привязки биллинга free tier
не работает. Деньги при этом не списываются, пока укладываетесь в
лимиты. Следите за бюджетными алертами, а не за жёстким лимитом
расходов: у Cloud Run срабатывание лимита **останавливает сервисы**
и они начинают отдавать 5xx.

### 2. Машина

```bash
gcloud compute instances create zhkhan-vm \
  --zone=us-central1-a \
  --machine-type=e2-small \
  --image-family=ubuntu-2204-lts \
  --image-project=ubuntu-os-cloud \
  --boot-disk-size=30GB \
  --boot-disk-type=pd-standard \
  --no-boot-disk-auto-delete \
  --scopes=https://www.googleapis.com/auth/cloud-platform
```

`--no-boot-disk-auto-delete` — чтобы случайное удаление инстанса
не унесло базу вместе с ним. Данные лежат на загрузочном диске
(`/opt/zhkhan/data`), отдельный том не нужен.

Для бесплатного e2-micro замените `--machine-type=e2-small` на
`--machine-type=e2-micro`.

### 3. Открыть порты

```bash
gcloud compute firewall-rules create zhkhan-allow-http \
  --allow=tcp:80,tcp:443 --network=default --source-ranges=0.0.0.0/0
```

### 4. Развернуть приложение

```bash
gcloud compute ssh zhkhan-vm --zone=us-central1-a
```

На машине:

```bash
curl -sSL https://raw.githubusercontent.com/cucumberbatch/ZhKhan-Agregator/main/deploy/setup_vm.sh | bash
```

Скрипт поставит Docker, создаст swap, соберёт образ, попросит вписать
токен бота в `/opt/zhkhan/.env` и запустит контейнер. Второй запуск
скрипта (после заполнения `.env`) доделает остальное.

### 5. HTTPS

Caddy ставится скриптом и сам берёт сертификат Let's Encrypt:

```bash
echo 'ваш-домен { reverse_proxy 127.0.0.1:8080 }' | sudo tee /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Без домена: откройте `http://<внешний-IP>:8080`, задав при старте
`BIND=0.0.0.0`. Работать будет, но без шифрования.

### 6. Проверка

```bash
curl http://127.0.0.1:8080/api/telegram
docker logs -f zhkhan
```

## Вариант C. Гибрид: e2-micro + Cloud Run Job (всё за $0)

Единственный способ получить полноценный бесплатный вариант в
Google. Смысл: машина не занимается скрейпингом, поэтому ей не нужны
ни Chromium, ни OCR, ни 416 МБ.

- **e2-micro ($0)** — отдаёт карту, API, SSE, держит SQLite и крутит
  бота. В простое 27 МБ.
- **Cloud Run Job ($0)** — ежедневный обход elicense.kz. Биллинг
  instance-based: 1 vCPU + 4 ГиБ × 300 с × 30 дней = 9 000 vCPU-сек и
  36 000 ГиБ-сек, что целиком входит в бесплатные 240 000 / 450 000.
- **Cloud Scheduler ($0)** — 3 задания в месяц бесплатно, у задания
  есть поле часового пояса, так что 3:00 по Астане настраивается
  напрямую.
- **Cloud Storage ($0)** — 5 ГБ бесплатно, туда кладутся результаты.

```bash
gcloud scheduler jobs create zhkhan-scrape \
  --location=asia-central1 --schedule="0 3 * * *" --time-zone="Asia/Almaty" \
  --http-target-uri="https://zhkhan-scrape-xxxx-uc.a.run.app/run" \
  --uri="https://zhkhan-scrape-xxxx-uc.a.run.app/run"
```

Что потребуется переделать в коде (это не переписывание, но работа):

1. Вынести обход elicense в отдельную точку входа, запускаемую без
   веб-сервера.
2. Результат обхода — объект в Cloud Storage, а машина забирает его
   и раскладывает в SQLite.
3. Убрать Chromium и OCR из образа на машине.

Плюсы: бесплатно, x86, настоящий диск, настоящий процесс 24/7.
Минусы: нужна доработка кода и ещё один компонент в инфраструктуре.

## После развёртывания: что настроить

| Переменная | Зачем |
|---|---|
| `TELEGRAM_BOT_TOKEN` | без неё бот не стартует; токен от @BotFather |
| `PUBLIC_URL` | адрес сайта в ссылках в сообщениях бота |
| `REFRESH_ENABLED` | `1` — ежедневное обновление (по умолчанию включено) |
| `REFRESH_HOUR` / `REFRESH_MINUTE` | время запуска по Астане, по умолчанию 3:00 |

### Первое обновление вручную

Планировщик ждёт 3:00 и молчит при первом запуске. Чтобы прогнать
сбор сразу:

```bash
curl "http://127.0.0.1:8080/api/refresh?run=1"
```

### Проверить, что бот жив

```bash
curl http://127.0.0.1:8080/api/telegram           # состояние и подписчики
curl "http://127.0.0.1:8080/api/telegram?test=1"   # тестовое сообщение
```

## Чего ждать на сервере

- **Капча elicense.kz с IP дата-центра.** С домашнего адреса капчи
  почти не бывает, с IP облака может быть чаще или могут начать
  блокировать. Это главный непроверенный риск. Проверяется так:
  после первого прогона посмотрите `docker logs zhkhan | grep -i капч`.
- **Первый обход занимает 1–2 часа.** Скорость ограничена капчей:
  примерно 45 секунд на застройщика, застройщиков около 70.
- **Холодный старт Chromium — 130 секунд**, а на shared-core
  e2-micro ещё дольше. Первый запрос после простоя будет долгим.
- **Telegram может быть недоступен из некоторых сетей.** С российских
  адресов `api.telegram.org` не отвечает — с сервера в США или Европе
  проблемы не будет.
- **Chromium в Docker.** Playwright рекомендует `--ipc=host` и особый
  seccomp-профиль; обычный Docker с ними справляется, а Cloud Run — нет
  (там песочница Chromium не заработает и нужен принудительный
  `--no-sandbox`).

## Откат

```bash
cd /opt/zhkhan && git pull --ff-only
docker build -t zhkhan:local . && docker rm -f zhkhan
bash deploy/setup_vm.sh
```

Данные в `/opt/zhkhan/data` при этом не трогаются.
