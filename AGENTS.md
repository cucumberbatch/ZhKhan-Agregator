# AGENTS.md

Карта жилых комплексов Астаны с датой начала строительства, взятой из
уведомлений elicense.kz. Python 3.10, без веб-фреймворков и без сборки.

## Команды

```bash
pip install -r requirements.txt
playwright install chromium          # без этого живой поиск не работает
python server.py                     # http://localhost:8000
```

## Тестовый режим

```bash
MAPTOOL_TEST=1 python server.py       # Windows PowerShell: $env:MAPTOOL_TEST="1"
```

Сервер не ходит в qportal, не геокодирует и не лезет на elicense.kz, а
отдаёт сохранённые ответы из `testdata/`. Нужен для правок вёрстки и
логики: полный цикл проверки одной строки в JS — это перезапуск,
прогрев кэша, ожидание SSE и только потом браузер. В тестовом режиме
страница готова сразу, дерево по застройщикам рисуется за 8 мс.

Фикстуры — это снятые с живого сервера ответы, то есть настоящие данные,
просто замороженные. Обновляются, когда состав данных изменился:

```bash
curl  http://localhost:8000/api/zhk     > testdata/zhk.json
curl  "http://localhost:8000/api/licenses?wait=1" > testdata/licenses.json
```

Если фикстуры нет или она битая, сервер в тестовом режиме скажет об этом
в логе и продолжит работать как обычно.

Сервер сам создаёт схему БД и один раз переносит данные из старых JSON.
Тестового фреймворка нет. `test_elicense.py` и `test_elicense_v2.py` —
не тесты, а ручные сценарии: они принимают БИН аргументом, запускают
Playwright с `headless=False` и печатают отчёт. Запускаются вручную,
в CI не участвуют.

## Устройство

- `server.py` — единственная точка входа: конфиг, сбор ЖК, все маршруты.
- `storage.py` — схема и потокобезопасный доступ к SQLite.
- `elicense_store.py` — чтение и запись уведомлений поверх `storage.py`.
- `elicense_client.py` — Playwright + ddddocr: поиск, капча, скачивание PDF.
- `elicense_html_parser.py` — разбор таблицы результатов elicense.
- `elicense_pdf.py` — извлечение полей из PDF уведомления.
- `zhk_match.py` — сопоставление уведомлений с ЖК.
- `index.html` — карта на Leaflet, без сборки и без зависимостей.

## Что легко сломать

**Playwright не потокобезопасен.** Sync-API объекты живут только в том
потоке, где созданы, а `ThreadingMixIn` отдаёт каждый запрос из своего.
Поэтому браузер живёт в `_BrowserOwner` — выделенном потоке с очередью.
Обращаться к нему только через `ElicenseClient`. Попытка создать
`sync_playwright()` в произвольном потоке даст
`cannot switch to a different thread`.

**Капча нужна только для поиска.** Страница карточки, список файлов и
само скачивание PDF работают без неё. Поэтому дозагрузку адресов
(`/api/elicense/enrich`) можно запускать часто — она дешёвая.

**Основной путь — БИН, а не название.** Название застройщика
разрешается в БИН через `resolve_developer_bin`: сначала кэш
`bin_cache` (наполняется при сборе ЖК из реестра qportal, там поле
`customer_bin`), затем DaData.

Поиск по названию на elicense.kz (поле «Лицензиат») оставлен
запасным (`/api/elicense?licensiat=…`), и вот почему: **сайт отдаёт
для него только первую страницу выдачи.** Замерено на БИН
`170440037274`: по БИН — 79 записей на 8 страницах, по названию — 10
записей на 1 странице, и все 10 совпадают с десятью самыми свежими.
Наш `total_pages()` насчитывает те же 8 страниц, но запрос `?page=2`
с фильтром «Лицензиат» сайт не отдаёт — таблицы нет. По БИН тот же
запрос работает. Фильтр применяется на стороне сайта уже после
выборки первой страницы.

Само сопоставление по названию при этом точное — ложных застройщиков
нет, сверка идёт по PDF-полю `applicant`. Не работает только глубина.

**Фильтр «Дата выдачи» уменьшает выдачу, и это уходит на сервер
сайта.** Проверено: 90 дней → 8 записей, 1 страница; без фильтра →
10 записей. Не полагайтесь только на клиентскую отсечку результата —
ограничение по дате надо передавать на сайт.

При широком окне на запасном пути в ответе появляется
`truncated: true` — **это нельзя игнорировать**, иначе тихо
покажется, что уведомлений не было.

**Срез по дате не должен обходить кэш.** `get_elicense_notifications`
сначала режет кэш, и только если в окне ничего нет — идёт в сеть.
Кэш хранит полную историю, а сайт при живом поиске отдаёт лишь
первую страницу, так что полный поиск по БИН надёжнее повторного.
Без этого каждый запрос платил бы капчей (~30 с) вместо 2 с.

**Русский язык выбирается параметром `lang=ru`, а не кнопкой на сайте.**
Без него elicense отдаёт казахские подписи, и парсер перестаёт находить
поля. В PDF язык выбирается по `Lang == "ru"` в ответе
`GetFileListByDocument` — не по тексту кнопки.

**Поля в форме поиска называются как в id HTML**, и один из них —
битовая маска, а не строка: `DateIssueEquality` (`1` Равно, `4` Больше,
`8` Меньше, `16` Не больше, `32` Не меньше) плюс `#DateIssueStr` в
формате `ГГГГ-ММ-ДД`.

**Хранилище ключуется по БИН, поэтому порядок записи важен.**
`save_result` для полного поиска по БИН авторитетна и удаляет записи,
которых нет в выдаче. Выдача поиска по названию подрезана фильтром «только
начало СМР» и полной историей не является — такой вызов обязан идти с
`merge=True`, иначе он стирает ранее собранное.

**UPSERT не должен затирать разобранное из PDF.** Ядро вставки
использует `COALESCE(excluded.col, table.col)`: парсер таблицы не знает
ни адреса, ни наименования объекта, и обычный upsert записал бы туда
`NULL`.

## Сопоставление с ЖК

Порядок в `zhk_match.match_notification`:

1. **Наименование объекта** — `object_name` из PDF против `name` из
   реестра qportal. Замер: 21 совпадение из 28, средняя оценка 0.80.
2. **Адрес как вето**, `ADDRESS_GATE_THRESHOLD = 0.15`.
3. БИН заявителя, затем геокодирование — запасные пути.

Две особенности, которые стоит помнить:

- В `name` из qportal часто входит и объект, и адрес
  («… , расположенный по адресу: город Астана…»), поэтому перед
  сравнением хвост отрезается функцией `clean_zhk_name`.
- Наименование **не уникально**: его используют десятки разных
  компаний, а у 22 застройщиков по несколько ЖК, у половины — с
  одинаковыми названиями. Поэтому кандидаты сначала сужаются по БИН
  заявителя из PDF, и лишь внутри этого набора выбирается по адресу.
  Без этого подбор уводит к чужому застройщику.

Адреса токенизируются с обрезкой слов до корня (`_STEM_LEN = 6`) и
склейкой «письмо + цифра»: PDF пишет `ул. Е117` и `Ж. Нәжімеденова`,
реестр — `улица Е 117` и `Жұмекен Нәжімеденов`. Без этого верные пары
не набирали порог.

## Фоновое обновление и телеграм

`refresh.py` — планировщик (поток, один запуск в сутки в 3:00 по
`Asia/Almaty`) и поиск изменившегося. `telegram_bot.py` — бот на
long polling, без вебхука: серверу не нужен белый IP, что важно для
бесплатного хостинга.

Три вещи, которые там легко сломать:

- **Первый запуск молчит.** Без этого каждый деплой рассылал бы
  «новые» объекты, которых не 135 сразу. Отключается через
  `REFRESH_NOTIFY_ON_FIRST_RUN=1`.
- **Дедупликация в БД**, а не в памяти: таблица `sent_notifications`
  по паре (вид, ключ). Иначе перезапуск приводит к повторной рассылке,
  а потеря одного уведомления — к тихому пропуску.
- **Без бота найденное всё равно помечается отправленным.** Иначе при
  первом же запуске с настроенным ботом прилетели бы все накопленные
  объекты разом.

Порядок в `perform_refresh` важен: сначала реестр проектов — из него
берутся БИН застройщиков, по которым потом опрашивается elicense.kz.
Перед этим кэш списка сбрасывается принудительно, иначе
`_zhk_cache` вернёт вчерашние данные и «нового» ничего не найдётся.

Управление без перезапуска: `/api/refresh` (журнал), `/api/refresh?run=1`
(прогнать сейчас), `/api/telegram` (подписчики), `/api/telegram?test=1`
(тестовое сообщение).

## Ловушки Windows

**`dddocr` печатает приветствие китайским при инициализации.** Консоль
в cp1251 — процесс падает `UnicodeEncodeError` до начала работы. Лечится
`_ensure_utf8_stdout()`. Не «глушите» вывод подменой `sys.stdout`:
потеряется строка лога из соседнего потока.

**`HTTPServer` разрешает повторную привязку порта.** Несколько копий
сервера молча делят 8000, и запросы уходят к старой — с выглядящим
правильным, но устаревшим кодом. Проверяйте, что на порту ровно один
процесс, или поднимайте на `MAPTOOL_PORT`.

**При запуске сервера из PowerShell кириллица в stdout превращается в
кракозябры**, а `python -c` падает на печати русских строк. Для
диагностических скриптов пишите отчёт прямо в файл:

```python
sys.stdout = open("_report.txt", "w", encoding="utf-8")
```

## Проверка изменений

Живой поиск медленный: холодный старт Chromium — около 130 с, OCR-модель
поднимается один раз на процесс.

- `/api/elicense/enrich?bin=…` — дозагрузка PDF, 4–70 с, капча не нужна.
- `/api/elicense?licensiat=…` — запасной путь по названию, 15–70 с с капчей.
- `/api/verify?address=…&developer=…` — проверка извлечения: верный адрес,
  чужая улица, другой город должны давать разные вердикты. БИН
  берётся из кэша реестра, затем из DaData — смотрите
  `resolved.source`: `cache` или `dadata`.
- `/api/elicense/match` — сопоставление с ЖК; смотрите `stats` и
  `unmatched[].reason`.

Окно дат переопределяется на запросе: `?months=6`, `?days=30`,
`?from=2026-09-01`, `?op=gt|lte|lt|eq`, `?all=1` — вся история.
Умолчание проверяйте так: срез из кэша отвечает за 2 с и содержит
`source: "cache"`; если вместо этого `source: "live"` и 30+ с — окно
оказалось пустым и ушло в сеть, либо задан `refresh=1`.

После изменения схемы или логики записи сверяйте количество строк в
`elicense_notifications` до и после: регрессии там проявляются как
тихое удаление накопленного.
